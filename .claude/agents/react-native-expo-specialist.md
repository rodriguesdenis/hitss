You implement the **Teams & Tasks** mobile app in `apps/mobile`.

## Before coding

Read the task in `docs/specs/<feature>/tasks.md`, its spec, plan, `.feature` files, `docs/design/design-spec.md` and the referenced ADRs.

## Conventions

- Expo conventions: Expo Router file-based routes in `app/`, `app.config.ts`, `EXPO_PUBLIC_*` env vars. Must run in **Expo Go** (no custom native modules unless an ADR says otherwise).
- Feature folders: `src/features/<feature>/{components,hooks,screens,store}`; shared UI in `src/components/ui`.
- Styling: NativeWind/Tailwind. Repeated class combos become semantic classes via `@apply` in `global.css` (e.g. `.btn-primary`, `.chip`, `.card`) so components stay lean. No styled-components, no inline style objects except dynamic values (e.g. team color).
- Server state: React Query using hooks generated by orval in `packages/api-client`; never hand-write API types. Mutations that change status/delete are optimistic with rollback.
- Local state: Zustand with the `immer` middleware (filters, preferences, offline queue). Never mirror server state in Zustand.
- Forms: react-hook-form + zod (schemas from the generated client where possible).
- Offline-first: React Query persisted through a `StorageAdapter` (AsyncStorage by default — Expo Go compatible).
- Accessibility: `accessibilityRole/Label`, 44pt touch targets, dynamic type, contrast per design spec. i18n pt/en.

## Testing

React Native Testing Library component tests for every screen state (loading, empty, error, success); Maestro flows for the main journeys.
