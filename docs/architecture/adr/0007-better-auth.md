# ADR-0007 — Better Auth for authentication

- **Status:** Accepted, partly superseded by [ADR-0020](0020-simplify-architecture-for-the-hiring-test.md)
- **Superseded (2026-10-22):** cookie sessions and the CSRF / Origin / JSON-body guards on `/api/v1` (Bearer tokens only now) — see ADR-0020.
- **Date:** 2026-10-20
- **Deciders:** software-architect, security-specialist, nestjs-specialist

## Context

The brief does not require authentication, but without it "teams and tasks" are global and any production note would start with "add auth". We scope every resource to an owner (constitution §VI.2), which needs a real identity. Constraints: the project must run **offline with one command** (no external identity provider), work in **Expo Go**, be callable with **cURL/Bruno**, and stay within the Nest ecosystem.

## Decision drivers

- Self-hosted, runs inside our container against our PostgreSQL.
- Secure defaults (password hashing, session rotation, CSRF/origin checks, rate limiting on auth routes) without writing crypto glue.
- Works for a native app (no browser cookies jar) **and** plain HTTP clients.
- Idiomatic NestJS integration: global guard, decorators, public-route opt-out.
- Small surface: email + password is enough for the scope.

## Considered options

### 1. Better Auth + Prisma adapter + `bearer` + `@better-auth/expo` (chosen)

- **+** TypeScript-first, framework-agnostic, stores users/sessions in our database through the Prisma adapter.
- **+** `bearer` plugin returns the session token in `set-auth-token`, so `Authorization: Bearer` works from cURL/Bruno.
- **+** `@better-auth/expo` (server plugin + `expoClient`) persists the session in `expo-secure-store` and handles the native origin; works in Expo Go.
- **+** Community package `@thallesp/nestjs-better-auth` provides a global `AuthGuard`, `@Session()`, `@AllowAnonymous()`, `@OptionalAuth()`.
- **−** Younger than Passport; the Nest integration is community-maintained (pinned version, covered by e2e tests).
- **−** Requires disabling Nest's body parser (`NestFactory.create(AppModule, { bodyParser: false })`) so Better Auth reads raw bodies; the module re-enables JSON parsing for other routes.

### 2. Hand-rolled Passport + JWT (`@nestjs/passport`, `@nestjs/jwt`)

- **+** Canonical Nest docs example; no third-party auth library.
- **−** We would own password hashing parameters, refresh-token rotation, revocation, sign-out semantics and brute-force protection — security-sensitive code with no product value.
- **−** Stateless JWTs make revocation (sign-out everywhere) hard without a denylist.

### 3. Hosted identity (Auth0, Clerk, Supabase Auth, Firebase Auth)

- **+** Battle-tested, MFA/social login for free.
- **−** Requires internet access, an account and secrets — breaks "clone + `docker compose up`" and offline evaluation.
- **−** Vendor lock-in and extra configuration for evaluators.

### 4. Lucia / Auth.js

- **−** Lucia is now a learning resource, not a maintained library; Auth.js targets web frameworks and has weaker native-app support.

## Decision outcome

- **Server:** `betterAuth({ database: prismaAdapter(prisma, { provider: "postgresql" }), emailAndPassword: { enabled: true, minPasswordLength: 8, maxPasswordLength: 128 }, plugins: [bearer({ requireSignature: true }), expo()], trustedOrigins: [...], advanced: { database: { generateId: "uuid" }, ipAddress: { ipAddressHeaders: ["x-tt-client-ip"] } }, onAPIError: { … } })`, configured from validated env (`BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`).
- **User ids:** UUIDs stored in `text` columns (D16). With `generateId: "uuid"` on PostgreSQL, Better Auth omits the id on insert and relies on the database, so every identity id column defaults to `gen_random_uuid()::text` (migration `create_identity_tables`). The Prisma models come from the Better Auth CLI (the `auth` package: `auth generate --adapter prisma`), mapped to snake_case and kept as `text` ids on purpose (the CLI would emit `uuid` columns). The domain keeps `ownerId` as an opaque string and never relies on its format.
- **Mount:** `@thallesp/nestjs-better-auth` `AuthModule.forRoot({ auth })` exposes Better Auth at **`/api/auth/*`** and registers a **global `AuthGuard`**. Every route is authenticated by default; `@AllowAnonymous()` is used only on health and docs (constitution §VI.1).
- **Ownership:** controllers read `@Session() session` and pass `session.user.id` as `ownerId` into commands/queries; repositories always filter by `ownerId`; foreign ids → `404`.
- **trustedOrigins:** the app scheme (`teamstasks://`) always, plus the explicit web origins from `CORS_ORIGINS`; `exp://` (Expo Go) only when `APP_ENV=local` (`APP_ENV` is `local` | `test` | `production`). (Better Auth's `expo()` plugin also adds `exp://` by itself when `NODE_ENV=development` — library behavior, so production images must not run with `NODE_ENV=development`.) A unit test pins the list per environment.
- **Mobile:** `createAuthClient({ baseURL, plugins: [expoClient({ scheme: "teamstasks", storagePrefix: "teamstasks", storage: SecureStore })] })`. Since ADR-0020 the API accepts only `Authorization: Bearer` on `/api/v1`: the app stores the signed token from `set-auth-token` in SecureStore and the generated client's mutator sends it as a Bearer header (not `authClient.getCookie()`).
- **Rate limiting:** `/api/auth/*` is served by Better Auth outside Nest controllers, so the Nest throttler cannot see it. Better Auth's **built-in limiter** (explicitly `enabled`, memory storage) applies per IP: `sign-up`, `sign-in`, `sign-out` 10 req/min each, per endpoint (`customRules`), everything else incl. `get-session` 100 req/min. The client IP comes from our client-IP middleware (see [Security controls](#security-controls)), never from client-controlled headers. Its `429` uses Better Auth's native format (with `X-Retry-After`). `/api/v1/*` uses `@nestjs/throttler` in two layers: a per-IP limit (300 req/min, configurable) that runs **before** `AuthGuard` (bounds anonymous and forged-token traffic) and 100 req/min per user after it, both answering `429 RATE_LIMITED` in our envelope. The per-IP layer is **open (T-001-15, release-blocking)** and must reuse `resolveClientIp`, so both limiters agree on the client.
- **Response format:** `/api/auth/*` keeps Better Auth's native responses and errors — a documented exception to the envelope (constitution §IV.2).
- **Logging:** request/response bodies are never logged; `authorization`, `cookie`, `set-cookie` and `set-auth-token` headers are redacted; query strings of `/api/auth/*` URLs are stripped; Better Auth's own `logger` is routed to pino at `warn`. Tokens, cookies and passwords never appear in logs ([threat model](../../security/threat-model.md#logging-redaction)).

### Security controls

| Control                | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Client IP              | Better Auth only reads the IP from request headers (it sees a Web `Request`, not the socket). With no resolvable IP it falls back to a single shared bucket, so one attacker could throttle every user. `clientIpMiddleware`, chained in the AuthModule `middleware` option after the route allowlist (so it runs before the Better Auth handler), deletes any incoming `x-tt-client-ip` and sets it from the TCP peer, or from `req.ip` only when `TRUSTED_PROXIES` is set (an IPv4-mapped `::ffff:a.b.c.d` peer is unmapped to one form); Better Auth reads only that header (`ipAddressHeaders: ["x-tt-client-ip"]`). `req.ip` is the socket address unless `TRUSTED_PROXIES` (CIDR list, empty by default) is set, which configures Express `trust proxy`. The same resolver (`resolveClientIp`) must feed the per-IP Nest throttler (T-001-15, open). Config refuses `/0` ranges everywhere, treats `::ffff:a.b.c.d/N` as IPv4 `/N-96`, and in production refuses ranges wider than IPv4 `/8` or IPv6 `/16`. Follow-up: when no address resolves (socket already closed) the request should fail closed instead of falling back to Better Auth's shared bucket. E2E tests use distinct loopback sources, read the resolved address back from `sessions.ip_address` (not Better Auth's test-mode fallback) and prove two addresses have independent buckets and that spoofed `x-tt-client-ip` / `X-Forwarded-For` never pick a fresh bucket. |
| Bearer tokens          | `bearer({ requireSignature: true })`: only the signed token from `set-auth-token` is accepted. A raw `sessions.token` read from the database (backup, SQL injection) is not a usable credential, and forged tokens fail the signature check without a session lookup.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| CSRF on cookie auth    | **Superseded by [ADR-0020](0020-simplify-architecture-for-the-hiring-test.md): Bearer-only on `/api/v1`.** `BearerAuthGuard` passes Better Auth only the `Authorization: Bearer` header, so a cookie never authenticates a business route and no CSRF guard or JSON-only (`415`) guard is needed there. `/api/auth/*` keeps Better Auth's cookie handling with its origin and Fetch-Metadata checks forced on in every environment. Browser clients now hold the token in script-reachable storage (XSS instead of CSRF exposure; threat model R-20).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Request size           | `/api/auth/*` bodies are capped at **16 kB** by a middleware in front of the handler (`413`, before any hashing); `/api/v1/*` keeps the 100 kB JSON limit. **Open — T-001-14, release-blocking:** the auth cap is not implemented yet (the 100 kB parser does not apply to `/api/auth/*`, which Better Auth reads raw).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Errors                 | `onAPIError` is configured so unexpected failures on `/api/auth/*` return a generic `500` without Prisma or SQL text; details go to logs with the `traceId`. Implemented with `onAPIError: { throw: false }`, logging `{ name, code }` only; **the database-failure e2e is open in T-001-14** (release-blocking).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Demo account           | Seeded only when `SEED_DEMO=true` (default `true` in the compose development profile). Config validation rejects `SEED_DEMO=true` with `APP_ENV=production`, so a known password never ships. Independently, `SEED_ON_START` (007: whether the container runs the seed step at all, default `true` locally) must be `false` when `APP_ENV=production`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Production config      | Startup validation fails when `APP_ENV=production` (production gating keys on `APP_ENV`, not `NODE_ENV`) and: `BETTER_AUTH_SECRET` starts with a placeholder prefix (`local-dev-`, `unit-test-secret-`) or is shorter than 32 chars; `DATABASE_URL` contains the local placeholder password; `SEED_ON_START=true`; `BETTER_AUTH_URL` is not `https`; `CORS_ORIGINS` contains `*`, `http://` or `localhost`; `AUTH_RATE_LIMIT_ENABLED=false`; `SEED_DEMO=true`. API docs follow `DOCS_ENABLED` (off by default when `APP_ENV=production`). Error messages name the variable, never its value. Rules land with the task that introduces each variable (007: secret, database URL, `SEED_ON_START`; 001: `BETTER_AUTH_URL`, `CORS_ORIGINS`, `AUTH_RATE_LIMIT_ENABLED`, `SEED_DEMO`). With `APP_ENV=production`, `.env` files are ignored: configuration comes only from the real environment.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Password policy        | Length only, 8–128 (NIST SP 800-63B), no composition rules, no trimming. Passwords are not Unicode-normalized (documented); breached-password screening is a production improvement.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Endpoint surface       | Only `/sign-up/email`, `/sign-in/email`, `/sign-out` and `/get-session` are served. The 25 other endpoints of this configuration (profile update, password change/reset, sessions list/revoke, email verification, social/account linking, Expo proxy…) are in `disabledPaths`; a unit test pins that list against the instance's real endpoints, so an upgrade that adds a route fails CI. An allowlist gate in front of the handler answers `404` for every other normalized path (parameterized routes, case variants, `%2F`, trailing slash). E2E: 29-row `404` table.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Origin and CSRF checks | Better Auth skips its origin check and Fetch-Metadata CSRF check by default when `NODE_ENV=test`, so the factory sets `advanced.disableOriginCheck: false` and `disableCSRFCheck: false` in every environment (unit-pinned). E2E: a sign-in from an untrusted `Origin` gets `403` with no `set-auth-token`, no `Set-Cookie` and no `sessions` row, on the allowlist and on the local `*` setup. `trustedOrigins` never contains `*`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

## Consequences

**Positive**

- Production-grade sessions (DB-backed, revocable) with very little code.
- Same identity works for the app and for humans: one signed Bearer token (stored in SecureStore on the device).
- The domain stays unaware of auth: it only sees an `ownerId`.

**Negative**

- Dependency on a community Nest adapter; mitigated by pinning and e2e tests on guard behavior (401 without session, public routes reachable).
- Identity ids are UUID values in `text` columns generated by PostgreSQL (`gen_random_uuid()::text`), not by the library; our tables reference `users.id` as `text`, and the schema deviates from the CLI output on purpose (documented in `schema.prisma`).
- Two limiters with two `429` formats (Better Auth native on `/api/auth/*`, envelope on `/api/v1/*`); clients handle both.
- The memory limiter storage is per instance; production with several instances would use secondary storage (Redis).
- Sign-up necessarily reveals that an email is registered (accepted risk, rate limited); production would use verification-first sign-up.
- Sliding sessions have no absolute lifetime; production would add an absolute maximum age with re-authentication.
- Session tokens and verification values are stored as issued (a signature is required to use a session token, so a database read alone is not a credential); production hashes them at rest. The OAuth token columns are unused; enabling social login requires `account.encryptOAuthTokens`.

**Neutral**

- Email verification, password reset and social login are out of scope but available as Better Auth options.
